# 转人工节点：话术与交接摘要

**用在哪**：条件分支命中 `need_human = true`、或 HTTP 节点连续失败时的兜底分支
**模型**：建议**直接套模板不走模型**（更省更快，而且转人工场景本来就要求话术稳定，不需要发挥）。
如果一定要走模型，用 `qwen-plus`，温度 0。

---

## 一、什么时候必须转人工

| 触发条件 | 判断方式 | 优先级 |
|---|---|---|
| 意图是 complaint | 意图节点输出 | 高 |
| 客户明确说转人工 | 意图节点输出 | 高 |
| 情绪 negative 且要求赔偿或威胁曝光 | 意图节点输出 | 高 |
| 资格判定返回 `requires_human = true`（超期、争议） | 接口字段 | 普通 |
| 连续 2 轮 confidence < 0.6 | 会话变量累加计数 | 普通 |
| 任何 HTTP 节点报错或超时 | 异常分支 | 高 |

不要什么都转人工。转人工率是核心指标，它飙升说明前面的识别或知识库有问题，
而不是"服务态度好"。健康区间参考 20%~35%。

## 二、给客户的安抚话术模板

分三种情绪，别用一套话术打天下：

**中性（单纯超出自助范围）**
> 这件事需要人工帮你核实一下，工单已经建好，编号 {{ticket_id}}，
> 预计 {{eta_minutes}} 分钟内接入。你的订单信息我一并带过去了，不用重复说明。

**不满（情绪负面、诉求合理）**
> 抱歉让你多等了，这事换谁都会不舒服。我已经把工单 {{ticket_id}} 标成加急，
> 预计 {{eta_minutes}} 分钟内接入，情况我都写进去了，不会再让你重复一遍。

**激动（辱骂、威胁投诉曝光）**
> 我理解你现在很生气。你的问题我处理不了，也不该由我敷衍你，
> 现在就转给人工主管，工单 {{ticket_id}}，预计 {{eta_minutes}} 分钟内接入。

三条硬规则：

1. 共情只说一句。连续道歉三行，客户反而觉得你在拖。
2. 必须给具体工单号和等待时长。没有这两样，客户会认为你在打发他。
3. 绝不说"这是规定""我也没办法"。把责任推给规则最招骂。

## 三、交给人工坐席的交接摘要（这才是重点）

转人工最怕客户把话重说一遍。所以工单必须带上下文：

```
【售后转人工】{{priority}}
客户诉求：{{reason_summary}}
意图：{{intent}}　情绪：{{sentiment}}　紧急：{{urgent}}
订单号：{{last_order_no}}
已查到的数据：{{tool_result 摘要，含金额、签收时间、规则码}}
已告知客户：{{上一轮回复要点}}
未解决原因：{{为什么转人工，如"已签收 40 天，超出无理由期限，需人工审核"}}
建议动作：{{给坐席的下一步，如"核实是否符合质量问题退货"}}
会话轮次：{{轮次}}　首响耗时：{{首响秒数}}
```

「未解决原因」这一栏决定了坐席能少问客户几句话。
面试时把这张模板拿出来，比讲一堆架构图更能证明你懂真实客服流程。

## 四、转人工之后要回流数据

个人项目做一个轻量闭环就够：

1. 工单表加 `resolved_by` 字段，标记 AI 自助解决还是人工解决。
2. 每周导出人工工单的「未解决原因」列，按频次排序。
3. 排前 3 的原因 → 要么补进知识库，要么改意图边界规则，要么调资格判定阈值。
4. 在 README 记一行迭代日志，例如：
   「第 2 周：价保类咨询占人工工单 18%，补充 3 条 FAQ 后降到 7%。」

这就是「数据驱动迭代」的完整证据链，比"我持续优化了提示词"具体一百倍。
