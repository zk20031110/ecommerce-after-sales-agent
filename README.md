# 电商售后客服 Agent（Dify + 通义千问）

一个跑在自部署 Dify 上的售后客服 Agent：能查订单、查物流、判定退换货资格、处理价保与发票、
在必要时转人工，并且**不会编造金额和时效**。

> 定位一句话：**把"查得到的"自动化，把"判不了的"交给人工，且不让客户重复叙述。**

技术栈：Dify 0.7.x（自部署 Chatflow）+ 通义千问 `qwen-plus` + FastAPI 模拟后端 + 1330 块知识库。

## 三、快速开始（四步）

### 1. 起模拟后端

```bash
cd mock-api
python -m pip install -r requirements.txt
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

**这个窗口会被服务器占住，别关，也别按 Ctrl+C。** 后面所有命令都另开窗口跑。

起好之后浏览器打开 **<http://127.0.0.1:8000/console>**——这是**坐席工作台**，
人工客服的界面：能看到排队中的工单、客户的完整对话记录、AI 已经查到的订单数据，
并直接接入、回复、提交退款、关闭工单。转人工不再是"弹个工单号就完事"。

**四个页面，对应三个角色：**

| 页面 | 给谁看 | 做什么 |
|---|---|---|
| <http://127.0.0.1:8000/> | 面试官 / 访客 | 入口页：架构、实时指标、迭代日志 |
| `/client` | 客户 | 和 AI 对话，转人工的起点 |
| `/console` | 人工坐席 | 接管工单、回复、转主管、关闭 |
| `/dashboard` | 产品 / 主管 | 转人工率、自助解决率、未解决原因排行 |

**客户端需要额外配一个 Key**：`.env` 里的 `DIFY_APP_KEY`
（Dify → 打开你的应用 → 左侧「访问 API」→ 创建密钥，形如 `app-xxxx`）。
不配也能打开页面，只是发送消息时会提示你去配。

### 2. 一键环境自检

```bash
python tools/check_env.py
```

它会检查：后端五个场景接口是否正常、Dify 是否可访问、知识库 API Key 是否有效。
全绿再往下走，能省掉一半排错时间。

### 3. 导入 DSL

浏览器打开 `http://localhost` 登录 Dify → **工作室** → **创建应用**旁的下拉 → **导入 DSL 文件** →
把 `dify/after-sales-agent.yml` 拖进去。

导入后画布上应该是 **24 个节点**：开始 → 订单号抽取 → 记录对话 → 情绪升级判断 →
意图识别（7 类）→ 各自的工具调用与回复。

### 4. 验证

在调试窗输入「订单 2024091288765 我要退货」，应该返回可退 269 元的方案。

## 四、应用架构

```
客户消息
   │
   ├─ 代码节点：正则抽取订单号（抽不到返回空串，后续节点会追问）
   │
   ├─ 问题分类器（qwen-plus，温度 0）→ 六个类别之一
   │
   ├─ 物流查询 ───► GET  查订单与物流 ──► qwen 话术化
   ├─ 退款退货 ───► POST 退款资格判定 ──► qwen 出方案
   ├─ 换货     ───► POST 换货资格判定 ──► qwen 出方案
├─ 通用咨询 ───► 知识库检索（1330 块）──► qwen 回答
   └─ 投诉/转人工 ► POST 建工单 ──► qwen 安抚（带真实工单号）
```

**为什么用问题分类器而不是 LLM 节点？** 分类器只需要选一个类别，不用生成 JSON，
更快、更稳、更便宜，也不会出现"JSON 解析失败"这类工程问题。
代价是拿不到置信度和次级意图——对当前的六类分流来说够用。

## 五、知识库素材（kb-assets/）

Agent 的"知道"来自知识库。这部分是独立模块，覆盖「生成 → 清洗 → 切块 → 向量化 → 入库 → 抽检」全链路：

| 素材 | 数量 | 格式 | 是否入库 |
|---|---|---|---|
| 产品手册 | 300（一 SKU 一份） | DOCX | ✅ |
| SOP 标准流程 | 200（售前/售后/投诉/物流 各 50） | DOCX | ✅ |
| 退换货政策 | 15（12 品类 + 3 通用） | DOCX + Markdown | ✅ |
| FAQ 清单 | 500 条 | XLSX | ✅ |
| 客服话术库 | 300 条 | XLSX | ✅ |
| 历史工单 | 150,000 条 | SQLite | ❌ 只挖掘 |
| 订单 / 物流 | 实时 | API | ❌ 现查 |

实测：**1330 份文档 → 1330 个块 → 约 25.4 万 tokens**，入库走 Dify 数据集 API，支持断点续传与小批量验证。

> 早期按长度切块是 1908 个块（约 32.3 万 tokens），但一条 QA 会被切成两半、答案串味；
> 改成 **FAQ 与话术库逐条成块**后归一为 1330 块——块数变少，检索质量反而上去了。

详细说明见 [kb-assets/README.md](kb-assets/README.md)。

### 知识库怎么分：三个库，不是一个大库

一开始所有素材塞进一个库，结果客户问「退货运费谁承担」，
向量检索召回的第一条是**一份砂锅的产品手册**——字面太像了。
实测 30 条检索用例，素材类型命中率只有 **43%**。

拆成三个库后（每个库用**文本专用**的 `text-embedding-v3` + 混合检索 + Rerank）：

| 知识库 | 装什么 | 文档数 |
|---|---|---|
| 01-政策与FAQ库 | 15 份政策 + 500 条 FAQ | 530 |
| 02-产品手册库 | 300 份产品手册 | 300 |
| 03-流程与话术库 | 200 份 SOP + 300 条话术 | 500 |

**检索效果对比**（30 条抽检用例）：

| 指标 | 单库混合 | 三库拆分 |
|---|---|---|
| 素材类型命中率 | 43% | **93%** |
| 关键词命中率 | 90%（注） | **83%** |

注：单库那个 90% 是虚高的——当时产品手册里塞了 FAQ 章节，同一句答案在两处出现，
召回命中哪一份都算"含关键词"。去掉重复后回落到真实水平。

在 Agent 里接法：Chatflow 的「知识库检索」节点勾选这三个库；
更彻底的做法是按分支接不同的库（政策分支只查政策库，产品咨询只查手册库）。

## 六、自部署 Dify 的三个必踩坑

**坑一：容器里的 localhost 不是你的电脑。**
HTTP 节点写 `http://localhost:8000` 会指向 Dify 容器自身。要写：

```
http://host.docker.internal:8000
```

验证方法（宿主机上解析不了这个域名是正常的，它是给容器用的）：

```
docker exec -it docker-api-1 curl -s http://host.docker.internal:8000/health
```

**坑二：知识库 id 填错不报错。**
检索节点的 dataset id 填错时，Dify 不提示任何错误，只是永远检索不到东西——
这是最难排查的一类问题。用 `python tools/check_env.py` 或
`python kb-assets/pipeline/upload_to_dify.py --list` 查真实 id。

**坑三：模型名严格区分大小写。** provider 必须是 `langgenius/tongyi/tongyi`，
模型必须是 `qwen-plus`，一字不能差。

## 七、怎么测

### 意图分类评测集

`tests/cases.jsonl` 共 46 条（另有 `cases_colloquial.jsonl` 44 条口语化用例），
覆盖全部 7 个类别，其中刻意埋了这些坑：

| 用例 | 陷阱 |
|---|---|
| C12「换不了就退了吧」 | 提到"换"就是换货，即使带"退" |
| C14「降价 50 能补差价吗」 | 价保属于通用咨询，不是退款退货 |
| C30「退款多久到账」 | 问规则属于通用咨询，不是要办理退款 |
| C31「再不来我就投诉你们」 | 核心是催件，不是真投诉 |
| C33「内衣能退吗」 | 问品类规则，不是要办理退款 |
| C35「我不想退，就是想问怎么保养」 | 否定词陷阱 |
| C09「买了 40 天了想退」 | 超期必须转人工，不许模型拍板 |

**在 Dify 里逐条测，记录三项：分类是否正确、是否调用了对应工具、回复里有没有编造数字。**

### 六个核心指标

| 指标 | 目标 | 怎么算 |
|---|---|---|
| 意图识别准确率 | ≥ 90% | 判对条数 ÷ 90 |
| 自助解决率（北极星） | ≥ 60% | 无人工介入即结束的会话 ÷ 总会话 |
| 转人工率 | 20%~35% | 工单接口调用数 ÷ 会话数 |
| 引用准确率 | ≥ 98% | 回复里的数字能在接口返回里找到的比例 |
| 首响时间 | ≤ 3 秒 | Dify 日志时间戳 |
| 误判放行率 | 0 | 不该退的说成能退的条数，**宁可多转人工** |

### 后端自测

```bash
python tests/smoke_test.py      # 145 项断言
python tools/validate_assets.py # DSL 与评测集规范校验
```

## 八、写进简历怎么表述

**不要写**"用 Dify 搭建了一个 AI 客服机器人"——这句话没有信息量，而且会让人以为你在投开发岗。
**要写决策和取舍**：

> 我做了一个电商售后 AI 客服系统，核心是把**规则判定从模型里拿出来**——
> 金额和资格结论全部由后端决定，模型只负责表达，所以它不会编造退款金额。

**完整的简历写法、面试问答、数据卡片、表述翻译表见
[docs/06-简历与面试材料.md](docs/06-简历与面试材料.md)**，包含：

- 三种长度的简历版本（一句话 / 三条 bullet / 详细项目经历）
- 12 个高频面试问答的完整回答要点
- 可背诵的数据卡片（含每个数字的来源，以及"哪些是实测、哪些是参考"）
- 工程话 → 产品话的表述翻译表
- 「你不会写代码，怎么做的？」这类必问题的应对

### 三条最值得主动讲的

1. **「什么不进知识库」比「什么进了」更能体现判断力**——订单物流走实时 API、
   工单只挖掘不入库、政策文档才进知识库。
2. **「AI 让位」是产品规则不是技术实现**——人工接管期间 AI 不再插话，工单关闭后自动恢复。
   这背后是对"人工接手后客户体验会怎样"的判断。
3. **数字要分清实测和参考**——检索命中率是在系统上实测的；工单量是合成数据；
   转人工率的健康区间是行业参考。主动区分比含糊过去可信得多。

| 周次 | 发现的问题 | 数据依据 | 采取的动作 | 结果 |
|---|---|---|---|---|
| W1 | 价保被当成退货处理 | 评测集 C14 判错 | 分类器指令里加"降价→通用咨询"规则 | 复测通过 |
| W2 | FAQ 答案被切散 | 抽检发现块边界切开 QA | 改为逐条成块 | QA 不再串味 |
| W3 | 检索串味：政策问题召回砂锅手册 | 类型命中率仅 43% | 拆分三个知识库 | 类型命中 93% |
| W3 | 手册与 FAQ 内容重复 | 同一答案在两份素材中各出现一次 | 手册删掉"常见问题"章节 | 消除重复源 |
| W4 | 615 个块没入库 | 库容 713 / 应为 1330 | 文档名加 chunk_id（原命名撞名被去重） | 1330 全入库 |
| W4 | 正确答案排不进 top3 | 「退款多久能到账」前 4 名全是"价保怎么申请" | 换掉多模态 embedding，改 `text-embedding-v3` + 混合检索 + Rerank | 关键词命中 83% |
| W4 | 批量上传丢文档 | 64 篇索引 error | 加对账脚本 `reconcile.py`，按真实状态校准台账 | 0 error |
| W5 | 签收满 7 天当天被判超期 | 边界用例失败 | 期限判定改按自然日（签收日 +7 天的 23:59:59） | 46 项测试全过 |

| W6 | 订单查询零校验 | 随便编个订单号就能查到别人的订单 | 大额退款要求手机号后四位核验；查询字段全部脱敏 | 防冒领 |

## 十、已知限制（写清楚反而加分）

1. **后端是模拟的**。五个订单是构造数据，真实场景需对接你所在平台的订单 API。
2. **知识库素材是合成的**。用于验证检索链路，不可作为对外承诺发布。
3. **会话状态存在后端内存 + SQLite**，没有做分布式；多实例部署需要换成共享存储。
4. **情绪识别只有分类器一层**。真实客服需要更细的升级策略（连续两轮负面就升级主管）。
5. **检索评分是人工的**。目前按 `kb-assets/tests/retrieval_cases.jsonl` 逐条比对，没有自动化打分。
