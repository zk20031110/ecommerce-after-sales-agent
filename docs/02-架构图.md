# 售后客服 Agent · 架构与设计决策

## 一、端到端数据流（24 个节点）

```
客户消息
   │
   ▼
① 代码节点「信息抽取」
   │        抽 order_no（抽不到返回空串）+ phone_tail（4 位数字，用于身份核验）
   ▼
①之二 HTTP「记录对话」→ 后端统计轮次与连续负面情绪
   ▼
①之三 条件分支「是否需要升级」
   ├ 连续负面 ≥ 2 次 → 直接转人工主管（**情绪优先于意图**）
   └ 否 → 继续下面的意图分流
   ▼
② 问题分类器（qwen-plus，温度 0）八个类别
   │        物流查询 / 退款退货 / 换货 / 价保 / 通用咨询 / 投诉情绪 / 转人工 / **确认提交**
   │
   ├─ 物流查询 ──► HTTP GET /api/order-query ──► LLM 话术化 ──► 回复
   │
   ├─ 退款退货 ──► HTTP POST /eligibility (refund) ──► LLM 出方案 ──► 回复
   │
   ├─ 换货 ─────► HTTP POST /eligibility (exchange) ──► LLM 出方案 ──► 回复
   │
   ├─ 价保 ─────► HTTP POST /eligibility (price_protection) ──► LLM 出方案 ──► 回复
   │
   ├─ 通用咨询 ──► 二次分类（政策规则 / 商品参数 / 流程时效）
   │              └─► 只查对应的那一个库（三个库各 1330 块之一）──► LLM 回答 ──► 回复
   │
   ├─ 投诉情绪 / 转人工 ──► HTTP POST /api/tickets ──► LLM 安抚 ──► 回复
   │
   └─ 确认提交 ──► HTTP POST /api/after-sales/refunds ──► LLM 告知结果 ──► 回复
```

设计的核心是**判定在外、表达在内**：所有规则判定都在后端接口完成，
模型只负责把结论翻译成客户能听懂的话。模型没有机会做业务判断，也就没有机会判错。

## 一之二、多轮对话怎么实现（这是最容易做成演示的地方）

**问题**：客户说「订单 X 我要退货」→ AI 答「可退 269 元，要提交吗？」
→ 客户说「好」→ 如果只按单轮设计，「好」会被判成「退款退货」，
**重新走一遍资格判定，把同一句话再说一遍**——客户永远等不到退款。

**解决**：把「确认提交」独立成第 7 个意图，并让会话状态记住订单号。

```
第 1 轮：订单 X 我要退货
   ① 代码节点抽出 order_no = X
   ② 分类器 → 退款退货
   ③ POST /eligibility  → 后端把 X 记进 session（键是 sys.conversation_id）
   ④ LLM 回复：可退 269 元，要现在提交吗？

第 2 轮：好
   ① 代码节点抽不到订单号，返回空串（不要紧）
   ② 分类器 → 确认提交
   ③ POST /refunds      → 后端从 session 取出 X，重新校验资格 → 真的提交
   ④ LLM 回复：已受理，退款单号 RF2600100101，1-7 个工作日原路退回
```

**会话状态放在后端，不放在 Dify 的会话变量里**，理由有三：

1. 会话状态本质是**业务系统的事**（这单在处理什么、走到哪一步），
   不是对话编排层的事；
2. 后端存可以持久化，Dify 重启或换实例都不丢；
3. DSL 少一层变量读写，节点更少、更不容易出错。

代价是 Dify 里看不到状态，排查时要去看后端日志——所以第 5 步加了 `/metrics`。

### 身份核验也走同一套机制

大额退款（≥ 300 元）提交时后端会要求手机号后四位：

```
第 2 轮：好
   → POST /refunds → 后端：金额 639 元，需要核验 → 返回 RULE-NEED-VERIFY
   → LLM：这笔退款 639 元，请提供下单手机号后四位

第 3 轮：2010
   ① 代码节点抽出 phone_tail = 2010
   ② 分类器：只发 4 位数字 → 确认提交
   ③ POST /refunds 带上 phone_tail → 后端核对通过 → 真的提交
```

关键点：**分类器指令里明确写了「只发 4 位数字 = 确认提交」**，
否则客户回一句 "2010" 会被判成通用咨询，跑去查知识库，流程就断了。

## 一之三、情绪升级：为什么要放在意图分流之前

客户连续两轮表达不满时，**不该再走自动流程**——这时候还让机器人查政策、念规则，
只会把人彻底惹火。所以链路设计成：

```
信息抽取 → 记录对话（统计连续负面）→ 条件分支
                                       ├ 连续负面 ≥2 → 直接转人工主管
                                       └ 否 → 意图识别 → 各分支
```

**情绪优先于意图**，这是真实客服的基本策略。

判定放在**后端**（`POST /api/conversation/turn`），不放在 Dify 里，原因：

1. 连续几轮算"连续"，是个可以调的策略（现在是 2 轮，以后可能是 3 轮 + 权重），
   放后端改一个常量就行，不用动工作流；
2. 需要跨轮次的状态，Dify 的条件分支只能看当前这一轮；
3. 同一套策略可以同时服务多个渠道（App / 公众号 / 电话）。

**现在的情绪判定是关键词粗筛**（投诉/差评/曝光/垃圾/气死…），这是 demo 的做法。
生产环境应该接情感分析模型，或者让 Dify 的分类器把 sentiment 传给后端——
这一点在代码注释里写清楚了，不装。

## 一之四、转人工为什么要带交接摘要

"不让客户重复叙述"是这套系统的核心承诺之一，落地就在工单里：

```
订单号：2024091288765
会话轮次：4　连续负面：2
客户原话：我的订单到哪了 ／ 太差了，我要投诉 ／ 你们这服务真是垃圾
```

坐席接手时一眼就知道发生过什么，不用问客户"您刚才说的是哪个订单"。
摘要由后端在建工单时自动生成（`storage.build_handoff`），
数据来源是持久化的消息表——不是让模型现编，是真实对话记录的截取。

## 二、为什么用问题分类器，不用 LLM 节点输出 JSON

| 维度 | 问题分类器 | LLM 节点 + JSON |
|---|---|---|
| 输出可靠性 | 只会选类别，不会跑偏 | 可能返回非法 JSON，需要代码节点兜底 |
| 速度 | 快（少生成内容） | 慢（要生成完整 JSON） |
| 成本 | 低 | 高 |
| 能拿到置信度 | 否 | 能 |
| 能拿到次级意图 | 否 | 能 |

选分类器的理由：**八类分流不需要置信度，也不需要次级意图**。
拿到 JSON 却没有下游用它，纯粹是工程负担。
代价是"判不准"时无法按置信度降级——所以指令里写死了"判不准选通用咨询，让知识库兜底"。

**通用咨询为什么要再分一次？** 因为一个检索节点挂多个库，等于把三个库合并回一个大库，
评测时"每个问题只查它该查的库"的口径就不成立了（实测线上会召回客服话术当政策依据）。
多一次分类调用约 ¥0.0014/轮，换的是检索结果可解释。

## 三、关键设计决策

面试官真正会追问的是"你为什么这么选"，所以每个决策都要能说出代价。

| 决策 | 备选 | 选择与理由 | 代价 |
|---|---|---|---|
| 规则判定放哪 | 让模型判断 / 接口判断 | **接口判断**：规则会变且涉及钱，模型不适合承担 | 需要维护后端，多了接口依赖 |
| 政策知识放哪 | 全塞提示词 / 知识库 | **知识库**：政策会改，改了要立即生效且可追溯 | 多一次检索，召回不准会答偏 |
| 分类粒度 | 10+ 细分类 / 6 粗分类 | **6 类**：类别越少越准，长尾交给 RAG | 拿不到细分意图，依赖知识库质量 |
| 工单数据 | 入知识库 / 只挖掘 | **只挖掘**：含客户隐私与临时状态，入库会被当成政策依据 | 需要额外写挖掘脚本 |
| 实时数据 | 定期同步入知识库 / 实时 API | **实时 API**：物流每小时都在变，入库必然过期 | 强依赖后端可用性 |

## 四、知识库分层

```
知识库（1330 块，向量检索）
  ├── 产品手册 300 份  → 商品参数、保养、保修
  ├── SOP 200 份       → 流程、时限、升级条件
  ├── 退换货政策 15 份 → 规则、时效、运费
  ├── FAQ 500 条       → 高频问答（逐条成块）
  └── 话术库 300 条     → 语气模板

不进知识库
  ├── 历史工单 15 万条 → 只挖掘高频 QA 补充 FAQ
  └── 订单 / 物流       → HTTP 节点实时查询
```

## 五、高频五问怎么答

**Q：你怎么保证它不瞎编？**
三层：接口只给结构化字段；提示词禁止引用未出现的数字；回复内容可对照接口返回人工抽检。
不是靠"我相信模型"。

**Q：分类判错怎么办？**
先量化基线（40 条评测集）。错的分两类：边界模糊的（"退款多久到账"被当成退款退货）
改指令加优先级规则；长尾没覆盖的补进知识库。判不准的一律落到通用咨询，不允许硬猜。

**Q：为什么不全自动？**
查询类全自动没问题，涉及钱的必须人工确认。这是产品风险控制，不是技术做不到。
误退一笔的成本远高于省下的那点人力。

**Q：知识库素材哪来的？**
脚本批量生成，1330 份文档全部由同一份 SKU 主数据派生，保证跨文档口径一致。
同时明确边界：工单只挖掘不入库，实时数据走 API。

**Q：上线后怎么迭代？**
盯两个数据：转人工率（高说明分类或知识库有问题）、工单的"未解决原因"。
每周按频次排前三的原因做一次修正，记在 README 的迭代日志里。
