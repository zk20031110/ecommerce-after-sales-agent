# 售后客服 Agent · 需求与指标定义

## 一、要解决什么问题

电商售后咨询有两个特征：**问题高度重复**（到哪了、能不能退、运费谁出），
**但答案又要依据具体订单**（签收几天了、商品用没用过）。

纯人工成本压不下来；纯 FAQ 机器人答不准，因为它不知道"你这单"的情况。

> **把"查得到的"自动化，把"判不了的"体面地交给人，且不让客户重复叙述。**

## 二、边界：什么做，什么不做

| | 内容 |
|---|---|
| **做** | 订单与物流查询、退换货资格判定与引导、价保、发票、物流异常催件、常见政策问答 |
| **做到一半** | 退款/换货的**提交**动作——Agent 只给方案和收集确认，实际提交要客户明确二次确认 |
| **不做** | 直接承诺赔偿、修改订单金额、处理支付纠纷、索要客户隐私信息 |

写清楚"不做什么"，比写清楚"做什么"更能体现产品判断力。面试常问这一条。

## 三、需求优先级

**P0（没有就不能上线）**

1. 识别客户意图并分流，识别不准时**追问**而不是硬猜
2. 查到订单真实状态与物流轨迹后回答，不编造
3. 退换货资格按规则判定，给客户明确结论与下一步
4. 命中投诉或负面情绪时转人工，并带上完整上下文
5. 任何接口故障都有兜底话术，不允许沉默或把报错抛给客户

**P1（显著影响体验与成本）**

6. 知识库问答：政策类问题不占人工
7. 敏感操作二次确认，防误提交
8. 转人工排队信息（工单号 + 预计时长）
9. 会话记忆：客户说"那退了吧"，不用再报一次订单号

**P2（后续迭代）**

10. 情绪升级预警（客户越说越气时提前转人工）
11. 主动服务：物流异常自动推送，不等客户来问
12. 多渠道接入（小程序、公众号、App 内嵌）

## 四、意图矩阵（七分类）

分类器当前只分六类，这是刻意的取舍：**类别越少，分类越准，分流越稳**。
更细的意图（价保、发票、尺码咨询）不单独分类，统一落到「通用咨询」，
由知识库覆盖具体问题——用 RAG 解决长尾，而不是无限扩张分类树。

| 类别 | 占比预估 | 处理方式 | 能否自助闭环 |
|---|---|---|---|
| 物流查询 | 28% | 抽订单号 → 查订单与物流 API | 能 |
| 通用咨询 | 25% | 知识库检索（政策 / FAQ / 手册） | 能 |
| 退款退货 | 18% | 资格判定 → **等客户确认** → 提交 | 半自动 |
| 投诉情绪 | 10% | 建工单 → 安抚话术 | 不能 |
| 换货 | 7% | 资格判定（exchange）→ 二次确认 | 半自动 |
| **确认提交** | 7% | 直接调提交接口（后端重新校验资格） | 半自动 |
| 转人工 | 5% | 建工单 → 排队信息 | 不能 |

**「确认提交」是必须独立出来的一类**，不是凑数。没有它，客户说"好"会被判成
「退款退货」，重新走一遍资格判定——AI 把同一句话再说一遍，客户永远等不到退款。
详见 `docs/02-架构图.md` 的「多轮对话怎么实现」。

占比是**假设值**，不是事实——这正是上线后要验证的第一件事。

**易混边界（写死在分类器指令里的优先级）**：

1. 提到"换"就是换货，即使同时说"退"
2. 降价、补差价、价保 → 通用咨询
3. 只是问规则/时效/流程 → 通用咨询；明确要办理 → 退款退货
4. 辱骂、威胁曝光、要求赔偿 → 投诉情绪
5. 判不准 → 通用咨询（让知识库兜底，不要猜成退款）
6. 单纯的确认词或 4 位数字 → 确认提交；但**"算了""先别退""再想想"这类反向表达
   绝不能判成确认提交**——一次误判就是一笔真实退款

## 五、指标定义

### 北极星指标

**自助解决率** = 无需人工介入即结束的会话数 ÷ 总会话数，目标 **≥ 60%**。

"结束"的定义要写死：客户在 AI 给出方案后 2 轮内没有再提同类诉求。
定义不写死，这个数字就可以随便美化，一问就露馅。

### 一级指标

| 指标 | 计算方式 | 目标 | 怎么测 |
|---|---|---|---|
| 意图识别准确率 | 判对类别数 ÷ 总数 | ≥ 90% | 40 条评测集 `tests/cases.jsonl` |
| 转人工率 | 转人工会话 ÷ 总会话 | 20%~35% | 统计 `/api/tickets` 调用次数 |
| 引用准确率 | 回复中数字能在接口返回里找到的比例 | ≥ 98% | 人工抽查 50 条 |
| 首响时间 | 用户消息到首条回复的秒数 | ≤ 3s | Dify 日志时间戳 |
| 平均对话轮次 | 总轮次 ÷ 会话数 | ≤ 3.5 轮 | Dify 会话记录 |
| 检索命中率 | 召回块包含正确答案的比例 | ≥ 85% | `kb-assets/tests/retrieval_cases.jsonl` |

### 护栏指标（防止为好看的数字牺牲体验）

| 指标 | 为什么必须看 | 红线 |
|---|---|---|
| 误判放行率 | 把不该退的说成能退，会造成真实损失 | 0（宁可多转人工） |
| 答非所问率 | 客户问 A 答 B，最伤信任 | < 3% |
| 重复追问率 | 已经给过的信息又问一遍 | < 5% |
| 无响应率 | 接口挂了但客户没收到任何话 | 0 |
| 检索串味率 | 召回的是别的品类的政策 | < 5% |

「引用准确率」和「误判放行率」最容易忽略，但面试官最爱问。

## 六、风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 模型编造退款金额 | 客户按错金额预期，产生纠纷 | 金额只来自接口；提示词要求逐字引用 |
| 分类判错走错分支 | 给出无关答案 | 边界规则写死在指令里；判不准落到通用咨询 |
| 客户误确认导致误退款 | 真实资金损失 | 二次确认由规则判断，不用模型 |
| 接口超时 | 客户干等 | HTTP 节点配超时 + 失败重试 |
| 检索到别的品类政策 | 用错规则回答 | 政策按品类分文档，切块时保留品类字段 |
| 知识库 id 填错 | 检索永远为空且不报错 | 用 `tools/check_env.py` 定期核对 |

最后一条是自部署 Dify 最隐蔽的坑：**配置错了不留痕迹**。

## 七、这套需求怎么来的

不是拍脑袋：先看 15 万条历史工单的分布 → 确定六类分流 → 挖出 1400 个知识库未覆盖的高频问题 →
补进 FAQ。需求优先级是数据推出来的，不是猜的。链路见 `kb-assets/README.md`。
