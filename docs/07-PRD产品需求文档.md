## 一、背景与问题

### 1.1 业务现状

电商售后咨询占客服进线的绝大部分，且高度集中：到哪了、能不能退、运费谁出、怎么开发票。
这些问题的**问法是重复的，但答案依赖具体订单**——同样问"能退吗"，
签收 3 天的能退、签收 40 天的不能退、用过的不能退、质量问题的又能退。

> 数据说明：本项目使用 15 万条**合成工单**验证链路，非真实业务量。
> 真实落地时需替换为平台实际工单数据重跑分布分析。

### 1.2 三方痛点

| 角色 | 痛点 |
|---|---|
| **客户** | 等待久；换一个客服就要重讲一遍；同一个问题得到不同答案 |
| **一线坐席** | 大量重复问答；被同样的问题反复打断；情绪劳动重 |
| **平台** | 人力成本随咨询量线性增长；服务质量依赖个人经验，不可复制 |

### 1.3 为什么"用 AI"和"为什么不全自动"

**用 AI 的理由**：客户问法千变万化（"我东西咋还没到啊？？？"），
规则引擎匹配不了，纯 FAQ 也答不准。

**不能全自动的理由**：LLM 擅长理解与表达，**不擅长精确计算和规则判定**。
而售后场景里最关键的恰恰是规则——退款金额、时限、资格，错一个就是真实资金损失。

**所以本产品的核心设计是分工**：

> **后端负责"算得准"，大模型负责"说得好"。模型没有机会做业务判断，也就没有机会判错。**

## 二、目标与非目标

### 2.1 产品目标（可量化）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 自助解决率（北极星） | ≥ 60% | 无需人工介入即结束的会话占比 |
| 转人工率 | 20% ~ 35% | **过高说明识别或知识库有问题，不是"服务好"** |
| 意图识别准确率 | ≥ 90% | 104 条评测集（54 标准 + 50 口语化），由 `tools/eval_intent.py` 自动跑分 |
| 引用准确率 | ≥ 98% | 回复中的数字能在接口返回里找到的比例 |
| 首响时间 | ≤ 3 秒 | 客户发消息到收到第一条回复 |
| **误判放行率** | **0** | 把不该退的说成能退——宁可多转人工 |

### 2.2 非目标（本版本明确不做）

写清楚"不做什么"比"做什么"更重要，它决定了方案的边界和成本。

| 不做 | 原因 |
|---|---|
| 售前导购、推荐、比价 | 与售后目标不同，会稀释意图分类的准确性 |
| 赔偿决策、价格谈判 | 涉资金且需权限，必须人工 |
| 语音、图片工单（v1） | 多模态会显著提高复杂度，先在文本上跑通 |
| 替代坐席工作台 | 本产品只负责"交接"，不重做客服系统 |
| 主动外呼/营销 | 合规风险高，与本产品目标无关 |

## 三、用户与场景

### 3.1 客户（主用户）

**核心诉求**：快速拿到准确答案，不用重复解释。

**典型场景**

| 场景 | 客户原话 | 期望 |
|---|---|---|
| 查进度 | 「我的货到哪了，订单 2024091288765」 | 3 秒内看到真实轨迹 |
| 要退货 | 「不想要了，退钱」 | 直接告诉我能不能退、退多少、怎么退 |
| 问规则 | 「退货运费谁承担」 | 拿到明确规则，不用自己翻 |
| 情绪爆发 | 「太差了，你们就是骗人的」 | **别再让机器人念规则了，给我人** |

### 3.2 一线坐席

**核心诉求**：接手时知道发生过什么，不用从头问。

**典型场景**：AI 转来一张工单，坐席打开就看到——客户诉求、已查到的订单数据、
AI 已经告诉过客户什么、为什么没解决、建议动作。

### 3.3 客服主管

**核心诉求**：知道系统哪里不行，怎么改。

**典型场景**：每周看"未解决原因排行"，把前三名转成改进项（补知识库 / 改规则 / 调阈值）。

## 五、功能详述（核心章节）

每条需求包含：**交互流程 → 验收标准 → 边界与异常**。
验收标准写成可测试的形式，直接对应回归测试用例。

### 5.1 意图识别与分流（R1）

**设计**：7 类意图，含**独立的「确认提交」类**。

| 类别 | 处理方式 | 能否自助闭环 |
|---|---|---|
| 物流查询 | 查订单与物流接口 | 能 |
| 通用咨询 | 知识库检索 | 能 |
| 退款退货 | 资格判定 → 等确认 → 提交 | 半自动 |
| 换货 | 资格判定（换货规则）→ 等确认 | 半自动 |
| 投诉情绪 | 转人工 | 不能 |
| 转人工 | 转人工 | 不能 |
| **确认提交** | 直接调提交接口 | 半自动 |

**为什么「确认提交」必须独立成类**：否则客户说"好"会被重新判成退款申请，
AI 把同一句话再说一遍——**客户永远等不到退款**。分类体系必须考虑对话的阶段状态。

**验收标准**

| 编号 | 标准 |
|---|---|
| AC1.1 | 「订单 X 我要退货」→ 判为退款退货 |
| AC1.2 | 「换不了就退了吧」→ 判为换货（提到"换"优先） |
| AC1.3 | 「刚买就降价了」→ 判为**价保**（要办理差价，不是退货，也不是通用咨询）；「价保期多久」→ 通用咨询（要解释） |
| AC1.4 | 「再不来我就投诉」→ 判为物流查询（核心是催件） |
| AC1.5 | 「好」「可以」「2010」→ 判为确认提交 |
| AC1.6 | 「算了不要了」「先别退」→ **不得判为确认提交**（误退款高危） |
| AC1.7 | 置信度低或判不准 → 归通用咨询并追问，**不猜成退款** |

### 5.2 订单与物流查询（R2）

**验收标准**

| 编号 | 标准 |
|---|---|
| AC2.1 | 订单号缺省时**追问**，不编造状态 |
| AC2.2 | 轨迹连续 48 小时未更新 → 判定为异常件，给出催件方案 |
| AC2.3 | 接口超时或报错 → 兜底话术 + 建议转人工，**不展示技术错误** |
| AC2.4 | 返回的信息中手机号脱敏，不返回完整地址 |

### 5.3 退换货资格判定（R3）

**规则优先级**（顺序即优先级，写死在后端）

```
1. 未签收            → 不办理售后，可催物流
2. 质量问题          → 走质保通道（不受 7 天限制，即使已使用）
3. 商品已使用        → 不支持无理由
4. 贴身用品/定制商品 → 不支持无理由
5. 数码已激活        → 不支持无理由
6. 食品类            → 不支持无理由
7. 换货申请          → 换货规则（限一次、7 天内、有库存）
8. 7 天内            → 可无理由退货
9. 7~15 天           → 需人工审核
10. 超过 15 天       → 需人工审核
```

**价保走同一个接口的另一个 `request_type`**（`price_protection`），规则单独一套：

```
1. 没有降价记录              → 不补差价，提示可转人工核实
2. 降价来自秒杀/优惠券/直播价/清仓 → **不参与价保**（看降价原因，不看降了多少）
3. 官方调价且在 15 天内       → 可补差价 = 实付金额 − 当前售价
4. 官方调价但超过 15 天       → 需人工审核
```

**为什么价保必须由后端算，不能交给知识库**：差价要用订单实付价减当前售价，
是规则问题不是知识问题。踩过——让知识库回答时，AI 答出"不支持退差价"，
和自家政策文档（15 天内可退）直接矛盾。**错在钱上，是最贵的一类错误。**
另外价保和退货是**两套话术**：客户只要 50 元差价，回复里不能说"请寄回商品"。

**验收标准**

| 编号 | 标准 |
|---|---|
| AC3.1 | 签收 3 天 → 可退，金额与接口一致 |
| AC3.2 | **签收满 7 天当天 → 仍可退**（按自然日算，不按 24 小时算） |
| AC3.3 | 签收 8 天 → 转人工，**不承诺结果** |
| AC3.4 | 质量问题 15 天 → 走质保通道，可退 |
| AC3.5 | 已换过一次 → 拒绝，并给出退货替代方案 |
| AC3.6 | 会员享 15 天无理由，优先级高于普通 7 天 |
| AC3.7 | 签收 5 天官方降价 50 元 → 可补差价 50 元，**不按退货话术** |
| AC3.8 | 签收 3 天降价 40 元，但来源是限时秒杀 → **不参与价保**，说明原因 |
| AC3.9 | 签收 20 天官方降价 → 超过 15 天价保期，转人工，不承诺 |

### 5.4 二次确认与提交（R4）—— 本产品最关键的需求

**交互流程**

```
客户：订单 X 我要退货
  → 系统查资格 → 给出结论与金额 → 问"要现在提交吗？"

客户：好
  → 系统**重新校验资格**（不信任上一轮结果）
  → 金额 ≥ 300 元时要求手机号后四位核验
  → 幂等提交 → 返回退款单号与到账时效
```

**三条硬约束**

1. **后端重新校验**：提交接口不复用第一轮的判定结果，重新跑一遍规则——
   不信任调用方传来的金额和订单号。
2. **二次确认由规则判断**：客户是否同意，用正则匹配判断，**不交给模型**。
   模型可能把"我再想想"当同意，一次误判就是一笔真实退款。
3. **幂等**：按会话 ID 去重，客户连点两次只退一笔。

**验收标准**

| 编号 | 标准 |
|---|---|
| AC4.1 | 客户确认后返回真实退款单号与时效 |
| AC4.2 | 同一会话重复提交 → 返回同一张退款单（幂等） |
| AC4.3 | 不符合资格却直接提交 → 被拒绝并说明原因 |
| AC4.4 | 金额 ≥300 元 → 要求手机号后四位；不符则拒绝并转人工 |
| AC4.5 | 指定商品名 → 只退该商品；匹配不到则整单处理 |

### 5.5 知识库问答（R5）

**检索按问题类型路由到单个库**（本需求的关键设计）：

| 问题类型 | 查哪个库 | 例子 |
|---|---|---|
| 政策规则 | 01-政策与FAQ库 | "退款多久到账""内衣能退吗""秒杀能价保吗" |
| 商品参数 | 02-产品手册库 | "瑜伽垫怎么清洗""空气炸锅功率多少" |
| 流程时效 | 03-流程与话术库 | "超期退货的流程是什么""要求三倍赔偿怎么回复" |

**为什么不能一个节点挂三个库**：那等于把三个库又合并回一个大库。
评测时是"每个问题只查它该查的那个库"（93% 类型命中率），
线上却挂三个库，等于**用一个没被测过的配置对外服务**——
实测会召回客服话术当政策依据。多一次分类调用（约 ¥0.0014/轮）换检索结果可解释。

**验收标准**

| 编号 | 标准 |
|---|---|
| AC5.1 | 政策类问题（运费/时效/价保）能命中知识库并给出依据 |
| AC5.2 | 知识库没有的内容 → 说明无法确认并建议转人工，**不编造** |
| AC5.3 | 商品参数类问题命中对应商品手册，不串到其他品类 |
| AC5.4 | 客户只表达情绪、没提诉求时 → 先共情再追问，**不查政策也不转人工** |
| AC5.5 | 政策类问题不走"流程与话术"库，商品参数类问题不串到其他品类 |
| AC5.6 | 回复里**不得出现"知识库""文档""资料""检索"**等内部字眼 |

### 5.6 转人工与坐席接管（R6）

**触发条件**（四类，收着用）

| 类型 | 条件 | 优先级 |
|---|---|---|
| 客户明确要求 | "转人工""叫真人来" | 高 |
| 强负面投诉 | 要求赔偿、扬言曝光/差评、辱骂 | 高 |
| 情绪升级 | **连续两轮**表达不满 | 高 |
| 业务规则要求 | 超期、金额超限、核验失败、接口故障 | 普通 |

**「AI 让位」规则（本需求的关键设计）**

工单处于「排队中」或「处理中」时：

- 客户的消息**不再进入 AI 流程**，只记录并转达人工
- AI **不再生成回复**，也不新建工单
- 工单关闭后，AI 自动重新接管

> 为什么必须有：实测遇到过——人工已接入并打了招呼，客户又说了句"我说了我要投诉"，
> 结果 AI 又建了一张新工单。人工在追新工单，客户觉得根本没人管他。

**验收标准**

| 编号 | 标准 |
|---|---|
| AC6.1 | 工单带坐席交接摘要（订单号 + 轮次 + 连续负面 + 客户原话） |
| AC6.2 | 坐席回复后，**客户 3 秒内在客户端看到** |
| AC6.3 | 人工接管期间客户发消息 → 不产生新工单、无 AI 回复 |
| AC6.4 | 工单关闭后 AI 恢复接管 |
| AC6.5 | 坐席工作台可见客户完整对话记录（不只是摘要） |
| AC6.6 | 关闭工单必须填「处理结果」与「未解决原因」 |
| AC6.7 | 同一工单被两个坐席接入时，第二个被拦截 |

### 5.7 情绪升级（R8）

**设计**：区分**强负面**与**弱负面**。

| 类型 | 例子 | 处理 |
|---|---|---|
| 强负面 | 要求赔偿、扬言曝光、辱骂、"太差了" | 直接转人工 |
| 弱负面 | "服务不太行""有点失望""体验一般" | **不转人工**，先共情再追问 |

**验收标准**

| 编号 | 标准 |
|---|---|
| AC8.1 | 「你们这服务不太行」→ 不转人工，先共情再问具体问题 |
| AC8.2 | 连续两轮负面 → 自动升级人工 |
| AC8.3 | 客户缓和（转为中性）→ 连续计数清零 |

### 5.8 会话管理（R9）

| 编号 | 标准 |
|---|---|
| AC9.1 | 客户第二句话不用重复报订单号 |
| AC9.2 | 关闭浏览器后再打开，历史对话自动恢复 |
| AC9.3 | 后端重启后会话不丢（订单号与对话映射持久化） |
| AC9.4 | 不同客户之间会话隔离，**不共用会话** |

## 六、AI 专项设计

### 6.1 模型分工

| 环节 | 模型 | 参数 | 理由 |
|---|---|---|---|
| 意图分类 | qwen-plus | 温度 **0** | 分类要可复现，同一句话两次判出不同结果就没法评测 |
| 回复生成 | qwen-plus | 温度 0.3 | 稍高温度让话术不生硬 |
| 向量化 | text-embedding-v3 | — | **必须用文本专用模型**，多模态模型中文区分度差 |

> 踩坑记录：早期用了默认的多模态 embedding，结果「退款多久能到账」的前 4 名
> 全是「价保怎么申请」。换文本专用模型 + 混合检索后恢复正常。

### 6.2 提示词设计原则

1. **结构写死**：结论 → 依据 → 下一步 → 收口。用小模型时靠结构弥补文采。
2. **负向约束要带例子**：不说"用中文"，而说"不允许出现 frustration、sorry、OK"——
   带反例的约束比泛泛要求有效得多。
3. **给编号开例外**：要求"只用中文"时必须排除订单号/工单号，否则会被模型改掉。
4. **长度限制**：手机上一屏放不下 5 行，超过就没人看。回复统一 ≤150 字。

### 6.3 幻觉防护（三层）

| 层 | 做法 |
|---|---|
| **数据源层** | 金额、时效、资格结论只来自后端接口，模型拿不到可自行计算的空间 |
| **提示词层** | 要求数字逐字引用，禁止"通常/大概"这类填充词 |
| **质检层** | 要求输出引用了哪些字段（`cited_fields`），抽检 50 条即可算引用准确率 |

### 6.4 降级策略

| 故障 | 降级动作 |
|---|---|
| 订单/售后接口异常 | 兜底话术 + 建议转人工，**不展示技术错误** |
| 知识库检索无结果 | 说明无法确认 + 建议转人工，**不编造** |
| 模型调用失败 | 提示稍后再试 + 建工单转人工 |
| 客户长时间未收到人工响应 | 提示排队进度 + 提供留言回电 |

### 6.5 人机协作边界

| 谁做 | 做什么 |
|---|---|
| AI | 理解意图、查询数据、组织表达、收集确认 |
| 后端规则 | 资格判定、金额计算、幂等控制、身份核验 |
| 人工坐席 | 超权限决策、情绪安抚、例外处理 |
| 主管 | 赔偿审批、投诉升级、规则调整 |

### 6.6 评测方案

| 评测对象 | 方法 | 用例数 |
|---|---|---|
| 意图分类 | 标准问法 + 口语问法两套用例分别跑，调真实工作流取回分类结果 | 54 + 50 |
| 知识库检索 | 30 条跨素材类型用例，看类型命中率与关键词命中率 | 30 |
| 业务规则 | 回归测试锁死边界行为 | 151 项 |
| 回复质量 | 人工抽检引用准确率 | 抽 50 条 |

## 七、数据与埋点

### 7.1 指标定义（口径写死，防止被美化）

| 指标 | 计算方式 |
|---|---|
| 自助解决率 | 无人工介入即结束的会话 ÷ 有对话的会话数。"结束"= 客户在 AI 给出方案后 2 轮内未再提同类诉求 |
| 转人工率 | 工单数 ÷ 有对话的会话数 |
| 平均轮次 | 会话平均消息轮数 |
| 引用准确率 | 回复中数字能在接口返回里找到的条数 ÷ 总数字条数 |
| 未解决原因分布 | 工单关闭时必填字段的频次排名 |

### 7.2 埋点需求

| 埋点 | 用途 |
|---|---|
| 每轮消息 + 所属会话 | 复盘、算平均轮次 |
| 意图识别结果 | 算准确率、找易混项 |
| 接口调用与耗时 | 排查性能、算首响 |
| 工单创建/接入/关闭 | 算转人工率、自助解决率 |
| 未解决原因 | **周度迭代的输入** |
| 满意度评价 | 服务质量 |

## 八、非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 首响 ≤3 秒；接口超时 5-10 秒并配置重试 |
| 安全 | 客服不索要验证码；订单信息脱敏；密钥不入代码库 |
| 合规 | 会话数据留存可追溯；模型输出不承诺规则外内容 |
| 可用性 | 任一依赖故障都有兜底话术，不允许客户收到技术报错 |
| 可维护 | 提示词集中管理；规则改动有回归测试保护 |

## 九、上线计划（灰度）

| 阶段 | 范围 | 观察指标 | 放量条件 | 回滚条件 |
|---|---|---|---|---|
| 内测 | 内部账号 | 功能可用性 | 主流程跑通 | — |
| 灰度 5% | 单一渠道 | 转人工率、误判放行率 | 转人工率 <35% 且无资金类错误 | 出现 1 次资金类错误 |
| 灰度 30% | 全渠道 | 上述 + 满意度 | 指标稳定 3 天 | 满意度显著下降 |
| 全量 | 全渠道 | 全指标 | — | 同上 |

**灰度期间必须人工复核的动作**：所有自动通过的退款申请 100% 抽查。

## 十、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 误判放行（不该退的说能退） | 真实资金损失 | 规则判定不在模型手里 + 二次确认 + 幂等；宁可多转人工 |
| 幻觉引用政策 | 客户投诉到平台 | 强制引用来源 + 抽检 |
| 会话串号 | 泄露他人订单信息 | 会话隔离 + 大额核验 |
| 人工接管后 AI 抢答 | 客户体验崩坏、重复工单 | 「AI 让位」规则 |
| 成本失控 | 预算超支 | 分批入库、分类用快模型、缓存高频问答 |
| 合规风险 | 监管处罚 | 不承诺规则外内容、隐私脱敏、会话留存 |
