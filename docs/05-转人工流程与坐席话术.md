# 转人工：完整流程与坐席话术

> 这份文档回答一个问题：**工单建好之后呢？**
> 只做到"弹个工单号"不叫转人工，那叫把客户丢出去。

## 一、什么情况才转人工

转人工是最贵的兜底手段，**必须收着用**。触发条件只有四类：

| 类型 | 触发条件 | 优先级 |
|---|---|---|
| 客户明确要求 | "转人工""叫真人来" | 高 |
| 强负面投诉 | 要求赔偿、扬言曝光/差评、辱骂、指责具体对象 | 高 |
| 情绪升级 | 客户**连续两轮**表达不满 | 高 |
| 业务规则要求 | 超期退款、金额超限、身份核验失败、接口故障 | 普通 |

**不能转的人工**：轻微抱怨（"服务不太行"）、单次负面情绪、判不准的意图。
这些应该先共情、再追问——转人工率一旦失控（>35%），
说明前两道（分类和知识库）有问题，而不是"服务态度好"。

---

## 二、阶段一：AI 触发时的告知话术

**必须包含三件事**：工单号、等待时长、已同步上下文。
缺任何一件，客户就会觉得被敷衍。

按情绪分三档，不要一套话术打天下：

**中性（业务规则要求转人工）**

> 这件事需要人工帮你核实一下，工单已经建好，编号 **{{ticket_id}}**，
> 预计 **{{eta_minutes}} 分钟**内接入。你的订单信息我一并带过去了，不用重复说明。

**不满（情绪负面，诉求合理）**

> 抱歉让你多等了，这事换谁都会不舒服。我已经把工单 **{{ticket_id}}** 标成加急，
> 预计 **{{eta_minutes}} 分钟**内接入，情况我都写进去了，不会再让你重复一遍。

**激动（辱骂、威胁曝光）**

> 我理解你现在很生气。你的问题我处理不了，也不该由我敷衍你，
> 现在就转给人工主管，工单 **{{ticket_id}}**，**{{eta_minutes}} 分钟**内接入。

三条硬规则：

1. **共情只说一句**。连续道歉三行，客户反而觉得你在拖。
2. **必须给具体工单号和时长**。没有这两样，等于没说。
3. **绝不说"这是规定""我也没办法"**。把责任推给规则最招骂。

## 三、阶段二：排队等待怎么安抚

**这是最容易被忽略、也最伤体验的一段。** 客户答完"转人工"之后如果没人说话，
30 秒就开始烦躁，90 秒就会再发一条"人呢？？"。

真实客服系统会有阶段性播报：

| 等待时长 | 播报内容 |
|---|---|
| 30 秒 | 人工正在查看你的订单，请稍等（不要只说"请稍等"） |
| 90 秒 | 前面还有 {{queue_position}} 位，预计还需 {{eta_minutes}} 分钟 |
| 超过预计 | 抱歉让你久等，已再次催办；你也可以留言，我们 30 分钟内回电 |

**留言回电是重要的兜底**：不是所有客户都愿意在线等，
给一个"先离开、我们主动找你"的选项，比让他在线干等强得多。

## 四、阶段三：坐席接入——决定体验成败的 30 秒

### 坐席打开工单时看到什么

这就是交接摘要的价值，也是"不让客户重复叙述"的落地：

```
【工单】TK26100410044903　　优先级：高
客户诉求：对服务不满，要求给说法
意图：投诉情绪　情绪：negative　连续负面：2 轮
订单号：2024091288765
已查到的数据：订单已签收 3 天，在 7 天无理由期内，可退 269 元
已告知客户：可退 269 元，需要客户确认后提交；客户表示要先投诉
未解决原因：客户情绪未平复，未进入退款流程
建议动作：先道歉安抚，确认客户是否仍要退款；如要退，直接帮客户提交
客户原话：我的订单到哪了 ／ 太差了，我要投诉 ／ 你们这服务真是垃圾
```

### 坐席第一句话（最重要的一句）

**必须承接上文，让客户知道你清楚状况。**

> ✅ 正确：「你好，我是人工客服小陈，工号 8801。我看到你反馈的是
> 订单 2024091288765 的退货问题，之前提到裙子尺码不合适，对吗？」

> ❌ 错误：「你好，请问有什么可以帮您？」

差别在哪：前者客户只需要点头，后者客户要把刚才说的全部再讲一遍——
**而他已经讲了三遍了。**

## 五、阶段四：坐席处理话术（按场景）

| 场景 | 客户说什么 | 坐席怎么接 |
|---|---|---|
| 客户抱怨重复描述 | "我刚才说过了" | 「我看到了，不用再讲一遍。我这边显示的是订单 X 的退货问题，对吧？」 |
| 客户情绪激动 | "你们就是骗人的" | 「你有这个感受我理解。」（先承认感受，**不要辩解**，辩解只会升级）；然后「我先帮你把退款提交了，好吗？」 |
| 客户要求赔偿 | "必须赔我钱" | 「你的诉求我完整记录了。赔偿需要主管评估，我无权直接定金额，现在帮你上报，会在 {{时限}} 前给你答复。」 |
| 客户问怎么办 | "那我现在要干啥" | 一次不超过 **3 步**：「第一步…第二步…第三步…」（步骤多了客户记不住） |
| 需要客户提供材料 | "要啥材料" | 「只需要两样：问题照片、订单号。其他我不问。」（明确"只要什么"，比列一堆强） |
| 权限不足 | "能不能免运费" | 「这个我可以帮你申请，但不能直接答应你。{{时限}} 内给你答复，可以吗？」 |
| 客户不接受方案 | "不行，我就要退" | 「我理解。这样，我先按你的要求提交，同时把情况反馈上去，两件事一起走。」 |
| 处理完成 | | 「已经处理完：退款 {{金额}} 元，单号 {{refund_id}}，{{时效}} 原路退回。还有其他需要吗？」 |

### 坐席的三条红线

1. **不承诺自己无权决定的事**（金额、时效、免运费）——先说"我帮你申请"，不说"可以"。
2. **不复述客户的过激用语**——客户说"垃圾"，你不要说"关于垃圾的问题"。
3. **不把责任推给第三方**——不说"这是快递的问题"，说"我帮你找快递核实"。

## 六、阶段五：结束与数据回流

### 结束话术

> 问题已经处理完：退款 **{{金额}}** 元，单号 **{{refund_id}}**，
> **{{时效}}** 内原路退回。还有其他需要吗？

三要素：**结论 + 依据（单号）+ 时效**。然后**主动追问一句**，
不要用"没有其他问题的话我就先结束了"——那是在赶人。

### 工单关闭时必须填的字段

这是整条链路最有价值的一环——**闭环**：

| 字段 | 取值 | 用途 |
|---|---|---|
| `resolved_by` | AI 自助 / 人工 | 算自助解决率 |
| `resolution` | 已退款 / 已换货 / 已解释 / 无解转主管 | 统计处理方式分布 |
| `unresolved_reason` | 超期政策 / 权限不足 / 客户不接受 / 情绪未平复 / 系统故障 | **周度迭代的输入** |
| `csat` | 1-5 分 | 满意度 |

**「未解决原因」这一栏是金矿**：每周导出按频次排序，
前 3 名要么补进知识库、要么改分类规则、要么调阈值。
这就是"数据驱动迭代"的完整证据链。

## 七、这套流程在项目里怎么跑

| 阶段 | 谁执行 | 对应实现 |
|---|---|---|
| 触发与告知 | AI | Dify 的「转人工建工单」节点 + 「生成安抚回复」节点 |
| 排队播报 | AI | 后端 `/api/tickets` 返回 `queue_position` 与 `eta_minutes` |
| 接入 | 坐席 | 坐席工作台（`mock-api/console.html`）打开工单 |
| 处理 | 坐席 | 工作台上的按钮：查订单、提交退款、转主管 |
| 结束 | 坐席 | 关闭工单并选择「未解决原因」 |
| 回流 | 产品 | 导出工单表，按 `unresolved_reason` 排序做迭代 |

坐席工作台是这套流程里**唯一给"人"用的界面**——它证明这套系统不只是给机器人看的。
